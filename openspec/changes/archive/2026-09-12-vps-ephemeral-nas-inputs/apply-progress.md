## Phase 3 remediation — HIGH finding: unvalidated `ValueError` crashed the whole materialize batch (branch `feat/vps-nas-2b`, on top of `ac9da55`)

Note on branch history since the Phase 3 entry above was written: the parent split slice 2 into two PRs before merging. `feat/vps-nas-2` (commit `49bc25f`, speaker_turns + trim_proposals + speaker_turn_videos together) was superseded — speaker_turns/trim_proposals merged to `dev` separately as PR #630 (commit `bb11ffd`), and `speaker_turn_videos_dag.py`'s wiring was recut as its own commit `ac9da55` on `feat/vps-nas-2b`, rebased onto `dev` tip `bb11ffd`.

The prior `is_archived_elsewhere` path never validated input and could not raise, so this was a genuine regression introduced by the D1/D6a inline-fetch wiring. `speaker_turns_dag.py`/`trim_proposals_dag.py` were unaffected — their per-item loops already wrap the whole per-item call in a generic `except Exception`.

Confirmed failing first (`ValueError: bad id` propagating out of `mod._materialize_task`) before the fix. Fix: added a `except ValueError as exc` clause to `_resolve_missing_source`, ordered before the existing `except nas_fetch.NasFetchError`, logging at `warning` level with the `video_id` and incrementing `summary["skipped"]` (same counter as `unavailable`) rather than `fetch_failed` — a malformed id is an input-format problem, not a NAS/rsync outage, so it must not count toward the D6 all-failed rule. The remaining plan in the batch still executes and materializes.
